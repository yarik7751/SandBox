# Подземелье: генерация уровней и новые механики

Дизайн-документ. Источник истины для реализации (в том числе в других чатах).
Статус: дизайн согласован, код не написан.

## Цель

Заменить статичный список из пяти уровней (`DungeonLevels.ALL`) на **условно
бесконечную** последовательность: уровень `N` детерминированно генерируется
из сида `f(N)`, проверяется solver'ом, par считается автоматически.
Существующие пять уровней остаются как начало последовательности
(уровень 1 уже выполняет роль обучения).

## Принятые решения

1. **Семантика клеток-укрытий**: враг не видит персонажа на тёмной клетке
   и **не входит** в неё. Укрытие = абсолютно безопасная зона, но через неё
   нельзя прогнать врага и нельзя спрятать приманку.
2. **Механика 3/4**: берём **дополнительный ход** (игрок ходит без ответа
   врага), оглушение отбрасываем — так враг страшнее.
3. **Интро-тексты**: у сгенерированных уровней — отказ, у рукотворных
   первых уровней остаются как есть.
4. **Генерация — вариант А (офлайн-пак)**:
   - генератор + валидация solver'ом гоняются в JVM-тестах в репозитории;
   - отобранные уровни записываются в **JSON-пак**, который зашивается
     в сборку (assets) и грузится при старте;
   - **предусмотреть возможность подгрузки новых паков**: формат паков
     версионируемый, id уровней глобально уникальны и стабильны
     (`bestTurns` в сейве ключуется по id), пак смотрится из assets
     по списку/индексу — добавление нового пака не меняет код чтения.
     Пока пак ровно один и прогружается при каждой сборке.

## Механики — вердикты и роль в генераторе

| № | Механика | Реализация (эскиз) | Вердикт |
|---|---|---|---|
| 1 | Недоступные клетки | `DungeonLevel.blocked: Set<Pos> = emptySet()`; фильтр в `DungeonGeometry.neighbors`, двери в `allDoors` не создаются; валидация в `create` (выход/улица/старты не в завале); solver: исключить из `openDistances` | ✅ первая |
| 2 | Клетки-укрытия | `DungeonLevel.concealed: Set<Pos> = emptySet()`; враг не целится (`DungeonEnemy.targets`) и не входит (тот же фильтр `neighbors`, что у завалов, но клетка проходима для героя) | ✅ после 1 |
| 0 | Заклиневшие двери | `DungeonLevel.jammed: Set<DoorId> = emptySet()`; `toggle` отклоняет; отдельная отрисовка (завал в проёме) | ✅ дёшево, настройка уровней |
| 6 | Лимит переключений | `DungeonLevel.togglesBudget: Int = Int.MAX_VALUE`; проверка в `toggle`, без траты хода при 0; **бюджет входит в `Key` solver'а**; solver считает минимально нужное число — бюджет ставится «оптимум + запас» | ✅ per-level |
| 5 | Враг раз открывает дверь | `DungeonLevel.enemyDoorCharge: Int = 0`; в `DungeonEnemy`: враг в ловушке и заряд > 0 → открывает соседнюю закрытую дверь, дающую путь к цели; **детерминизм обязателен** (tie-break по DIRS); **заряд входит в `Key`** | ✅ после дверной оси |
| 3/4 | Дополнительный ход | действие/ресурс, ход без ответа врага; поле в состоянии, **входит в `Key`**; оглушение не делаем | ⚠️ последняя, опционально |

Общий принцип: каждая механика — поле с дефолтом в `DungeonLevel`/`DungeonState`.
Пять существующих уровней, сейв (`unlockedLevel`, `bestTurns: Map<Int, Int>`)
и эвристика solver'а не ломаются.

## Архитектура генерации

```
индекс N → сид f(N) → параметры уровня (формулы от N) → раскладка (rng от сида)
        → валидация solver'ом (решаем? par в разумном диапазоне? не тривиален?)
        → JSON-пак (assets) → приложение читает пак при старте
```

- **Детерминизм**: сид = `f(N)`, уровень `N` одинаков везде и всегда;
  хранить уровни не нужно, только id. Соседние уровни отличаются и
  раскладкой (сид), и правилами (наклон параметров).
- **Валидация**: property-тесты в `core/dungeon` — «N сидов → каждый решается
  в пределах бюджета раскрытий, par в диапазоне, выход не завален».
- **Solver**: динамическое состояние (бюджет, заряд, доп. ходы) обязано
  входить в `Key`; статичное — нет. Эвристика остаётся допустимой:
  ограничения только урезают множество путей.
- **Пак**: формат JSON, id уровней глобально уникальны; чтение пака —
  отдельный компонент, список паков расширяем (пока один).

## Прогрессия — наклон, а не тиры

Параметры — непрерывные функции индекса + джиттер ±1, чтобы соседние
уровни отличались не только раскладкой (черновик, точные коэффициенты
подбираются по результатам solver'а):

```
сетка:              4×4 → 5×5 (с ~10) → 6×6 (с ~25)
заклиневшие двери:  0 → +1 каждые ~4 уровня
завалы:             0 с ~15-го, +1 каждые ~5 уровней
укрытия:            с ~30-го
бюджет переключений: ∞ до ~35, потом 8 → 6 → 5
второй пленник:     с ~30-го
заряд врага:        с ~40-го
доп. ход:           после дверной оси, с лимитом
```

## Порядок внедрения

1. Механики 1 → 2 → 0 (статичные, дёшевы для solver'а).
2. Генератор сидов в `core` + property-тесты на решаемость → JSON-пак.
3. Чтение пака в приложении (assets), лента уровней в UI вместо
   фиксированной сетки.
4. Дверная ось: 6 → 5.
5. Дополнительный ход — опционально, в конец.

## Открытые вопросы (не блокируют старт)

- Точные коэффициенты наклона прогрессии — по данным solver'а.
- Нужен ли в UI индикатор par/бюджета/заряда врага — решается при
  внедрении дверной оси.

## Контекст для реализации

- Ядро: `core/dungeon` — чистые функции, состояние неизменяемое,
  переходы через `DungeonEngine.act`.
- Враг: полностью BFS-driven, tie-break детерминирован по `DIRS`
  (up, left, right, down) — новые решения врага обязаны следовать этому.
- Solver: A* в `core/dungeon/src/test/.../solver/DungeonSolver.kt`,
  ключ состояния — `connectivityRegions` (union-find по открытым дверям).
- Правила workflow проекта: план с эскизами → «ок» → код → `./gradlew detekt`.
- Документ обновлять по мере принятия решений.
